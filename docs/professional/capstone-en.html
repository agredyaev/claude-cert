    CCAR-P · Capstone

    End-to-end architecture evidence

    Evidenced 0 / 14

    Use one realistic system. The point is not a toy implementation; it is evidence that one architecture survives design, integration, evaluation, governance, operations, and handoff.

    Artifacts

    9 architecture artifacts

    01

    Problem frame & constraints

    Define the user/business outcome, explicit non-goals, prohibited behavior, quality target, latency/availability target, cost envelope, data sensitivity, reversibility, and decisions that remain human-owned.

    Check acceptance criteria
    • Measurable success criteria exist.
    • Hard constraints are separated from preferences.
    • Irreversible/high-consequence decisions have an owner.
    • Non-goals prevent architecture creep.
    not evidenced
    02

    Architecture decision record

    Choose workflow vs agentic vs augmented-LLM architecture, model tier, context strategy, and orchestration pattern. Record at least two rejected alternatives.

    Check acceptance criteria
    • Decision is tied to stated constraints.
    • At least two plausible alternatives are rejected for explicit trade-offs.
    • Complexity is justified rather than assumed.
    • Revisit triggers are defined.
    not evidenced
    03

    Integration & trust-boundary map

    Map APIs, MCP servers, retrieval/data stores, credentials, authorization, tool capabilities, trust boundaries, and failure propagation.

    Check acceptance criteria
    • Every external capability has an auth boundary.
    • Least privilege is explicit.
    • Failure paths are visible, not only happy paths.
    • Sensitive data movement is traceable.
    not evidenced
    04

    Evaluation & release gates

    Define representative evaluation data, metrics, deterministic checks, model/human graders where needed, slice-level regressions, and release-blocking thresholds.

    Check acceptance criteria
    • Metrics correspond to user/business risk.
    • Critical slices cannot be hidden by aggregate scores.
    • Release gates are defined before the test result is known.
    • Regression runs are repeatable.
    not evidenced
    05

    Safety & governance matrix

    For each material risk, define preventive control, detective control, corrective action, owner, evidence artifact, and residual risk.

    Check acceptance criteria
    • Controls are placed before irreversible actions when possible.
    • Human review follows a risk rule, not blanket review.
    • Each risk has an accountable owner.
    • Evidence can be audited later.
    not evidenced
    06

    Cost & latency budget

    Model call/token assumptions, cacheable prefixes, routing, batching, throughput, tail latency, and the thresholds that trigger architecture changes.

    Check acceptance criteria
    • Budget assumptions are explicit.
    • Optimization preserves the evaluated quality/safety floor.
    • Tail latency is considered, not only averages.
    • Caching/routing choices have invalidation or fallback rules.
    not evidenced
    07

    Observability & operations

    Define traces, metrics, alerts, slow-drift reviews, incident ownership, and first diagnostic actions for retrieval, prompt, model, tool, and permission failures.

    Check acceptance criteria
    • Signals map to specific failure layers.
    • First diagnostic action is stated for each major failure class.
    • Ownership and escalation are explicit.
    • Slow quality drift is covered in addition to outages.
    not evidenced
    08

    Stakeholder brief

    Explain the same architecture for executive/security/legal stakeholders in terms of value, trade-offs, residual risk, reversibility, ownership, and evidence.

    Check acceptance criteria
    • Technical details are translated into business consequence.
    • Residual risks are not hidden.
    • Trade-offs are presented with alternatives.
    • Decision/approval owners are clear.
    not evidenced
    09

    Handoff package

    Create the runbook, architecture rationale, open assumptions, owner map, change criteria, known failure modes, and enough evidence that another architect can safely modify the system.

    Check acceptance criteria
    • Another team can operate and change the system.
    • Assumptions and unknowns are explicit.
    • Decision rationale survives team handoff.
    • Change/revalidation triggers are documented.
    not evidenced
    Failure injection

    5 stress tests

    1. Stale retrieval after refresh

    A content refresh completes, but answers still cite old facts. State where you investigate first, what evidence confirms the failure layer, and the structural fix.

    not evidenced

    2. Over-privileged tool

    A tool can mutate resources outside the task scope. Redesign the control boundary without relying on prompt instructions.

    not evidenced

    3. Hidden evaluation regression

    Aggregate quality improves after a model/prompt change while one regulated user slice degrades. Decide the release outcome and diagnostic path.

    not evidenced

    4. Cost / latency drift

    Tail latency and cost rise after context/caching behavior changes. Identify evidence needed before changing the model or architecture.

    not evidenced

    5. Irreversible stakeholder request

    A stakeholder requests an action the agent can execute autonomously but that cannot be safely reversed. Place the approval/control boundary and justify it.

    not evidenced
